# How AI was used

This document answers the four questions in the brief: which AI tools I used, what they generated,
what I changed or refined, and how I verified that the result is correct. It also explains the
workflow I set up so that AI-generated work could be trusted.

**In short:** I owned the requirements, the design decisions and every acceptance test. AI agents
generated the code, tests and first drafts of the documentation inside a workflow that I designed
and that enforces its own rules. Nothing reached `main` without passing tests I had approved and an
independent review.

## 1. Which AI tools I used

| Tool | Model | Role |
| ---- | ----- | ---- |
| Claude Code 2.1 (main session) | Claude Opus 5.5 | Planning with me, coordinating the agents, integration |
| `test-author` agent | Claude Opus 5.5 | Writing tests from the specification, before any code exists |
| `implementer` agent | Claude Sonnet 5.5 | Writing production code until the approved tests pass |
| `reviewer` agent (read-only) | Claude Opus 5.5 | Reviewing each feature against the specification and a checklist |
| `doc-writer` agent | Claude Sonnet 5.5 | Drafting documentation from real program output |

The agents, skills and hooks are part of the repository (`.claude/`), so the workflow can be
inspected and repeated. I used no other AI tools.

## 2. What code was AI-generated

Practically all of the code, tests and scripts, and the first drafts of the documentation, were
generated by the agents above. Each artefact came from a fixed source and passed a fixed check:

| Artefact | Generated by | Generated from | My role |
| -------- | ------------ | -------------- | ------- |
| Specification (`docs/SPEC.md`) | Main session | My requirements and decisions | Defined scope and acceptance criteria; approved the text |
| Tests | `test-author` | The specification | Approved every test list before any code was written |
| Production code | `implementer` | The approved, locked tests | Reviewed the diffs and the review findings |
| Documentation | `doc-writer`, main session | Real output of the CLI and API | Edited and approved |
| Project scaffolding | `dotnet new` templates | - | Chose the solution layout |

**What I did not delegate:** interpreting the requirements, the scope, the technology and workflow
choices, every public interface, approving each test list and each package, deciding what to do
with review findings, and the final review of the submission.

## 3. What I changed or refined

Every feature went through the same loop: tests first, then code, then an independent review. I
then decided what to change. These are the main decisions I made along the way.

### Correctness

- Numbers that `decimal` would silently round are rejected instead of being changed behind the
  user's back.
- When an input has several problems, the leftmost one is reported, and syntax errors always come
  before calculation errors.
- A non-zero result is never displayed as `0`. Rounding of very long results stays within
  `decimal`'s 28-29 digits, as a documented rule.
- I required a check that the independent test oracle can actually fail: deliberately breaking its
  operator precedence produced 1,257 reported failures, which were then reverted.

### User experience

- I defined the console contract: injected input and output streams, and exit codes 0, 1 and 2.
- Error output is safe for any terminal: the caret stays aligned, and control characters in piped
  input cannot inject terminal escape sequences.
- Interactive errors go to stderr, the session always exits with 0, and commands are
  case-insensitive.
- Questions show their interpretation before any error in the translated text.

### Service contract

- The API is tested in the Production configuration, not only in Development.
- Requests are strict: unknown JSON fields are rejected with 400, and every error is an RFC 9457
  Problem Details response with a trace id.
- Error positions in a translated question refer to the interpreted expression, which the response
  always includes.

### Security and cost

- Host filtering protects the MCP endpoint against DNS rebinding.
- Language-model replies are restricted to arithmetic characters, so the service cannot be used as
  a general-purpose AI proxy.
- Model calls have a timeout, an output-token cap, no retries and rate limits. The tool
  descriptions forbid the model from computing answers itself.

### Dependencies

- I approved the only three runtime packages (OpenAPI, the MCP SDK and an OpenAI-compatible client)
  and removed one the code did not need.
- The test-only packages also needed my approval. Any new package or tool always requires it.

### Design

- I kept the console app as one class, because its three modes share one evaluation path.
- Duplicated logic was extracted, for example one operator-to-symbol mapping and one response
  mapper shared by REST and MCP.

## 4. How I verified correctness

1. **Acceptance criteria first.** The specification, including `10-2*6/4 = 7`, was agreed before any
   code existed.
2. **Separate authors for tests and code.** Tests were written and approved before implementation,
   and the implementing agent could not change them. Hooks enforced this, and a git check after each
   implementation confirmed it.
3. **An independent oracle.** A reference evaluator built on a different algorithm (shunting-yard)
   agrees with the engine on 2,000 seeded random expressions. Property tests check that extra
   whitespace and re-parsing the canonical form never change a result.
4. **Mutation testing.** Stryker.NET injected small bugs into the engine, and the tests detected
   97.44% of them. Before I added targeted tests, the figure was 88.21%.
5. **Real surfaces.** Smoke tests run the real binary. API tests run in the Production pipeline. MCP
   is tested through a real MCP client, and a scripted fake model sends hostile replies.
6. **Gates on every change.** Every commit, and CI on Ubuntu and Windows, runs a strict build
   (warnings are errors), the analyzers, a format check, a package vulnerability audit and all 385
   tests.

## 5. Approach and key decisions

The brief is small, so I treated it as a chance to show judgement: correct results, clean
boundaries, honest verification, and AI used as a disciplined team rather than as a code generator.

- **A pure engine with thin hosts.** The calculator is a library with no dependencies. The console
  app, the REST API and the MCP server only adapt it. An engine that knows nothing about its user
  interface is reusable, easy to test and safe to expose as a service.
- **Parse completely, then evaluate.** Nothing is calculated until the whole input is valid. The same
  rule protects the AI path: whatever a model produces is parsed by a strict grammar and never run.
- **Correctness over convenience.** I chose `decimal` over `double`, invariant culture everywhere,
  rejection of numbers that would be rounded, and located error messages instead of raw exceptions.
- **The model translates; the engine calculates.** Deterministic rules come first, because they are
  free, fast and reproducible. A model is an optional fallback, constrained to strict JSON and
  treated as untrusted input. Through MCP, an assistant's own model does the translation, so this
  service needs no API key and has no model cost.
- **A proof of concept that is free to run.** REST, MCP and natural-language input all work without
  paid keys. A local model can be plugged in through configuration, which also covers on-premises
  use.
- **Modern, standalone .NET 10.** Minimal APIs, source-generated JSON, Problem Details, OpenAPI,
  built-in rate limiting and central package management.
- **Supply chain as a first-class concern.** The engine and the console app have no runtime
  dependencies, I approve every package, and vulnerable packages fail the build.

How I used AI responsibly:

- **Prompts are suggestions; hooks are enforcement.** Each agent can write only in its own area: the
  agent that writes tests cannot touch production code, and the reverse. The implementer cannot
  finish while anything is failing, nothing is committed without the quality gate, and new
  dependencies need my approval.
- **Detect what cannot be prevented.** Shell commands can bypass file-level hooks, so every
  implementation is followed by a git check that the locked tests are unchanged.
- **The reviewer is stronger than the worker.** Reviews run on a stronger model than implementation.
- **Human attention where it matters most.** Tests are the specification, so I reviewed and approved
  every test list. Work arrived as small, reviewable feature branches.
- **Verification beyond coverage.** An independent oracle and mutation testing show that the tests
  catch bugs, not merely that they execute code.
- **Transparency.** The git history shows me as the accountable author, and this document states
  exactly how AI was used.

## 6. Guardrails at a glance

| Rule | Enforced by |
| ---- | ----------- |
| Each agent writes only in its own area: `test-author` in `tests/`, `implementer` in `src/`, `doc-writer` in the documentation, `reviewer` nowhere | `PreToolUse` hooks in the agent definitions (`.claude/hooks/path-guard.sh`) |
| The implementer cannot stop while tests fail; nothing failing is committed; the full gate runs before `main` | `.claude/hooks/gate.sh`, run on `Stop` and on `git commit` |
| Locked tests stay unchanged during implementation | Write areas, plus a git check in the `/feature` skill |
| Every package, SDK, package-source or tool change needs a human | `ask` permissions and `.claude/hooks/dependency-gate.sh` |
| No force-push, every push needs a human, no network tools | Permissions in `.claude/settings.json` |

`scripts/guardrail-selftest.sh` checks the hooks with 18 test cases, and live probes confirmed that
each agent is blocked outside its area.
